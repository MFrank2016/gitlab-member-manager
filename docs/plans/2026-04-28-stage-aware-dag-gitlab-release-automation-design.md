# 分阶段 DAG GitLab 发版自动化设计

日期：2026-04-28
状态：已确认（brainstorming 定稿）

## 1. 背景

当前仓库已经具备一套可用的 `pipeline_*` 流水线底座：

- 本地 Git 节点执行
- GitLab 流水线检查、等待、触发
- 调度器与运行监控页
- 中文失败摘要与技术证据

但现有模型仍以“线性节点序列”为核心，主要能力是：

- 顺序执行一组节点
- 跨项目并发
- 对单个项目或执行段保留运行历史

这与当前目标存在明显差距。目标场景是一个发布链路编排器，要求：

- 本地仓库执行 `checkout/pull/merge/push`
- 多项目之间存在明确依赖
- 阶段之间串行
- 阶段内步骤可并行
- 全流程支持 GitLab 流水线门禁
- 可视化编辑 DAG
- 失败后给出中文结论，并支持阶段级和步骤级重试

因此，本次不在现有线性 `pipeline_nodes.node_order` 模型上继续叠补丁，而是将其升级为“带阶段语义的 DAG 发布编排器”。

## 2. 目标与边界

### 2.1 功能目标

- 支持以 DAG 方式可视化定义发布流水线
- 支持阶段之间串行、阶段内节点并行
- 支持本地 Git 节点与 GitLab 节点混合编排
- 支持手动触发运行，并保留现有调度能力的接入点
- 支持节点等待态持久化与运行监控
- 支持整条流水线、阶段、节点三级重试
- 所有失败提示默认使用中文，并附带技术证据

### 2.2 非目标

- v1 不做任意脚本执行
- v1 不做完全自由的任意 DAG 语言
- v1 不接入真正的 CICD 发版平台执行最终发布
- v1 不做自动通知，由用户根据日志人工通知
- v1 不做原地断点恢复，只做派生新运行
- v1 不做后台系统服务化守护，调度仍依赖桌面应用保持打开

## 3. 核心决策

### 3.1 采用“带阶段语义的 DAG”，而不是纯线性模型

流水线定义将升级为：

- 流水线
- 阶段
- 节点
- 边

原因：

- 用户的业务语义天然是“阶段间串行、阶段内并行”
- 阶段不是 UI 分组，而是执行边界
- 如果继续基于线性节点序列模拟并行，后续重试、失败阻断和监控都会快速失控

### 3.2 阶段是一等实体，不是视觉标签

`stage` 将作为独立持久化对象存在，而不是放到节点参数或画布元数据里。

原因：

- 阶段顺序需要直接驱动执行器
- 阶段需要独立运行状态与失败摘要
- 阶段需要提供重试入口
- 运行页需要准确表达“卡在哪个阶段、为什么下游没启动”

### 3.3 保留 DAG 表达力，但限制为可维护的业务子集

系统不会开放“完全自由任意图”，而是增加以下约束：

- 每个节点必须归属一个阶段
- 边只能连接同一流水线内的节点
- 禁止成环
- 禁止从后序阶段指向前序阶段
- 允许：
  - 同阶段内依赖
  - 前序阶段节点依赖到后序阶段节点

这样可以保留表达力，同时避免把系统演化成难以校验的通用工作流引擎。

### 3.4 编辑器直接复用开源图组件

前端编辑器采用 React Flow（`@xyflow/react`）作为图编辑基础设施。

原因：

- React 项目集成成本低
- 原生支持 `node + edge`
- 支持自定义节点
- 支持连接点与连接校验
- 支持 group / sub-flow，适合表达阶段容器

不选择“自己造拖拽画布”，因为那会把大量精力浪费在基础图交互上，而不是业务约束与运行语义上。

### 3.5 重试统一采用派生新运行

不做原地重跑，统一创建新的派生运行，并保留来源运行关系。

支持：

- 整条流水线重试
- 阶段重试
- 节点重试

原因：

- 历史审计清晰
- 不污染原始失败现场
- 更容易展示重试链路
- 后续接入真正发版节点时也更稳

## 4. 总体架构

系统分为四层。

### 4.1 定义层

负责描述“应该如何运行”：

- `pipeline_definitions`
- `pipeline_variables`
- `pipeline_stages`
- `pipeline_nodes`
- `pipeline_edges`
- `pipeline_schedules`

### 4.2 运行层

负责描述“这次运行发生了什么”：

- `pipeline_runs`
- `pipeline_run_stages`
- `pipeline_run_nodes`

运行层继续保留：

- 运行参数快照
- 中文失败摘要
- 技术证据
- 等待态上下文
- 来源运行关系

### 4.3 能力层

继续复用现有能力：

- `git_executor.rs`
- `gitlab.rs`
- `gitlab_executor.rs`
- `failure_envelope.rs`

其中真正需要升级的是调度器与 DAG 运行时，而不是底层 Git/GitLab 适配器。

### 4.4 交互层

前端拆为三块：

- 流水线画布编辑页
- 运行监控页
- 调度与基础配置页

画布负责结构编辑，侧栏负责参数编辑，运行页负责状态解释与重试入口。

## 5. 数据模型

### 5.1 定义模型

#### `pipeline_definitions`

保留现有主表，继续承载：

- 名称
- 描述
- 启用状态
- 版本
- 默认并发上限

#### `pipeline_variables`

继续保存流水线级变量定义，例如：

- `${feature_branch}`
- `${dev_branch}`
- `${remote}`

#### `pipeline_stages`

新增阶段表，建议字段：

- `id`
- `pipeline_definition_id`
- `stage_key`
- `name`
- `stage_order`
- `enabled`
- `created_at`
- `updated_at`

#### `pipeline_nodes`

在节点定义中增加阶段归属与画布位置，建议字段：

- `id`
- `pipeline_definition_id`
- `stage_id`
- `node_key`
- `node_type`
- `parameters_json`
- `position_x`
- `position_y`
- `enabled`
- `created_at`
- `updated_at`

#### `pipeline_edges`

新增节点依赖边表，建议字段：

- `id`
- `pipeline_definition_id`
- `source_node_id`
- `target_node_id`
- `created_at`

### 5.2 运行模型

#### `pipeline_runs`

继续保存：

- 触发方式
- 总体状态
- 运行参数快照
- `source_pipeline_run_id`
- 重试类型
- 重试起点

#### `pipeline_run_stages`

新增阶段运行表，建议字段：

- `id`
- `pipeline_run_id`
- `pipeline_stage_id`
- `stage_order`
- `stage_name_snapshot`
- `status`
- `summary_message`
- `started_at`
- `finished_at`
- `created_at`
- `updated_at`

#### `pipeline_run_nodes`

保留现有节点运行表，并补充阶段归属快照与重试状态语义。

继续保留：

- `stdout`
- `stderr`
- `error_code`
- `title_zh`
- `detail_zh`
- `suggestion_zh`
- `evidence`
- `wait_target`
- `last_remote_status`
- `remote_pipeline_id`
- `wait_context_json`

### 5.3 状态设计

建议状态：

- 运行：`pending` / `running` / `waiting` / `completed` / `partial_failed` / `cancelled`
- 阶段：`pending` / `running` / `waiting` / `success` / `partial_failed` / `failed` / `cancelled` / `reused`
- 节点：`pending` / `running` / `waiting` / `success` / `failed` / `skipped` / `cancelled` / `reused`

其中 `reused` 用于表达“本次重试未重新执行，而是复用上次已成功结果”。

## 6. 节点模型与首期内置节点

### 6.1 原则

继续采用“原子节点 + 明确依赖边”，不做复杂复合节点。

原因：

- 节点职责清晰
- 执行日志粒度明确
- 失败定位更准确
- 重试范围更容易计算

### 6.2 首期节点

本地 Git 节点：

- `switch_project`
- `set_working_path`
- `checkout_branch`
- `git_pull`
- `git_merge`
- `git_push`

GitLab 节点：

- `check_pipeline`
- `wait_pipeline`
- `trigger_pipeline`

后续真正发版平台接入时，再新增单独的“发布节点”，不提前在 v1 中占位实现。

### 6.3 GitLab 等待语义

`wait_pipeline` 需要优先等待“与当前运行上下文绑定的那次 commit / pipeline”，而不是简单等待某个分支最新流水线。

仅在明确配置为“分支健康检查”场景时，才允许查询分支 HEAD 的最新流水线。

原因：

- 避免被其他人的后续提交污染判断
- 保证当前自动化流程等待的是它自己触发或指向的那次远端运行

## 7. 执行语义

### 7.1 阶段串行、阶段内并行

执行器按阶段推进：

1. 进入当前阶段
2. 找出依赖已满足的节点
3. 在阶段内并行执行这些可运行节点
4. 当前阶段全部成功后，进入下一阶段

### 7.2 失败阻断

当某个节点失败时：

- 当前阶段中尚未启动的节点不再调度
- 已经启动的并行节点继续跑完
- 当前阶段收敛为失败或部分失败
- 后续阶段不再启动

这是 v1 选定的失败策略。

### 7.3 等待态

等待中的节点必须持久化：

- 等待目标
- 最近一次远端状态
- 远端流水线 id
- 下次轮询间隔
- 已等待时长
- 与等待相关的上下文

这样运行页才能解释：

- 在等什么
- 为什么还没结束
- 下一次会何时继续轮询

## 8. 重试语义

### 8.1 整条重试

从头创建新的 `pipeline_run`，继承原运行参数快照，允许用户在重试前覆盖少量变量。

### 8.2 阶段重试

从目标阶段开始创建派生运行：

- 目标阶段之前的成功阶段标记为 `reused`
- 从目标阶段重新调度全部节点
- 下游阶段按正常规则重新执行

### 8.3 节点重试

从目标失败节点开始创建派生运行：

- 与目标节点无关的成功节点标记为 `reused`
- 仅重跑目标节点及其下游依赖链

### 8.4 重试可见性

运行页必须展示：

- 来源运行 id
- 重试类型
- 重试起点
- 本次是否覆盖了原参数

## 9. 前端交互设计

### 9.1 编辑页

采用三栏布局：

- 左侧：节点面板
- 中间：React Flow 画布
- 右侧：属性面板

阶段以 group 节点或容器形式展现，节点卡片以自定义节点组件渲染。

### 9.2 保存与校验

保存前执行静态校验：

- 阶段顺序完整
- 节点必须归属阶段
- 边合法
- 无环
- 节点参数完整
- 变量引用合法

### 9.3 运行页

运行页新增阶段维度视图，至少回答四个问题：

- 当前卡在哪个阶段
- 哪个节点失败
- 为什么后续阶段没启动
- 是否可以从阶段或节点发起重试

## 10. 中文失败模型

继续复用当前结构化失败信封：

- `error_code`
- `title_zh`

- `evidence`

- 中文失败结论默认外显

## 12. 落地顺序

建议按以下顺序实施：

1. 定义模型升级：引入 `pipeline_stages`、`pipeline_edges`
2. 执行器升级：从线性运行时升级为阶段化 DAG 运行时
3. 重试升级：补齐阶段级与节点级派生重试
4. 编辑器升级：接入 React Flow 并替换现有线性表单
5. 运行页升级：增加阶段视图、阻断解释与重试入口
6. 后续再接真正 CICD 发布节点

## 13. 结论

本次设计的核心不是“再造一个通用工作流平台”，而是把当前项目升级为一个面向发布链路的、带阶段语义的 DAG 编排器。

这条路线的价值在于：

- 最大化复用现有 Git / GitLab / 失败信封 / 运行监控能力
- 最小化线性模型继续膨胀带来的技术债
- 让后续接入真正发版平台时只需要新增节点能力，而不是再次重写编排内核
